# Design

## Context

See `proposal.md` for the user-visible motivation. 当前 ChatSurface 在发送时会先创建本地用户项，随后并行处理 Session 状态、历史分页和事件流；历史项使用分页索引生成 ID，状态快照还可能补充待处理交互项。需要在不改动 Prompt API 和 canonical 消息存储的前提下，让这些来源合并为一个稳定的消息投影。

## Goals / Non-Goals

**Goals:**

- 以用户消息为不可丢失的投影事实，合并异步状态、历史和实时事件时保持其可见性。
- 对同一条已落盘 Prompt 做可预测的历史回放与去重，并保留文件问题和附件摘要的展示解析。
- 发送完成后维持合理的会话滚动位置，让用户能看到刚发送的问题；用户主动离开底部时不强制抢回滚动。
- 通过组件单测和真实 UI smoke 测试覆盖发送、运行结束、刷新恢复和文件附件场景。

**Non-Goals:**

- 不引入服务器文件上传、临时文件路径或新的附件存储服务。
- 不修改 Nexum Protocol、Server HttpApi 或 canonical Prompt 的内容格式。
- 不把完整文件正文渲染到用户气泡中。

## Decisions

### 1. 在 ChatSurface 内统一合并消息投影

状态和历史应用都使用保留当前项的合并策略；历史项先按稳定的历史索引去重，再与已有的即时用户项按 Prompt 内容进行等价匹配。这样可以保留即时展示，同时在历史加载完成后用持久化项完成恢复。相比每次直接替换数组，这能避免异步响应覆盖刚创建的用户项；相比只依赖事件流，刷新后仍可从历史恢复。

### 2. 以用户消息内容作为即时项与历史项的有限匹配键

当前 Prompt API 没有返回消息 ID，因此前端不能依赖不存在的服务端 ID。对于用户项，使用解析前的完整 Prompt 内容进行匹配，并保留历史项中的文件展示解析；对不同时间发送的相同问题不做跨消息全局折叠，只在当前即时项与同一历史批次合并时去重。相比按显示文本匹配，该方案不会把不同文件正文但相同问题误合并。

### 3. 滚动策略只修复发送后的可见性，不改变用户主动阅读行为

发送时明确恢复跟随最新消息，并在首个用户项插入后让聊天区域滚到底部；后续只有 `followTail` 为真时才跟随流式内容。用户滚动到历史区域后，保留现有“回到底部”入口，不强制跳转。相比每次收到历史/事件都滚到底部，该方案不会打断用户阅读。

### 4. 用真实 UI smoke 覆盖历史恢复

在现有浏览器 smoke 中验证：发送带文件 Prompt 后用户问题和附件摘要立即可见；运行完成后仍可见；页面刷新重新加载同一 Session 后仍可见且不重复。组件投影单测覆盖新旧文件 Prompt 解析及消息合并边界。这样测试的是实际 adapter、Server 和浏览器渲染链路，而不是复制实现逻辑的 mock。

## Risks / Trade-offs

- [Risk] Prompt 内容可能很长，前端等价匹配会增加一次线性扫描成本 → 仅在历史/当前消息合并边界执行，并按用户项建立索引，避免在每个事件上扫描完整正文。
- [Risk] accepted 响应早于 Core 持久化完成时立即刷新，历史页可能暂时不含新 Prompt → 保留即时项，后续历史/事件刷新再次合并；不会因一次短暂的历史缺口删除它。
- [Risk] 滚动高度变化可能让用户消息在长回复下离开视口 → 发送时恢复跟随最新消息，并保留用户主动滚动后的手动控制。

## Migration Plan

1. 发布仅包含前端投影与测试的修复，不需要数据迁移或服务端部署顺序调整。
2. 保持现有完整 Prompt 历史格式，旧版文件上下文继续按兼容解析规则显示。
3. 若出现回归，可回滚 ChatSurface 变更；已保存的 canonical 消息不受影响。
